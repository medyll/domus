# S1-05: Implement batching scheduler

**Story ID:** S1-05
**Status:** Done
**Epic:** MVP 1 - Reactive Core
**Points:** 5

## Description

Implement effect batching to prevent multiple effects from running synchronously when multiple Signals are updated. Use `requestAnimationFrame` to batch updates into a single render cycle.

## Acceptance Criteria

- [ ] `batch<F: FnOnce()>(f: F)` function that defers effect execution
- [ ] Effects added to queue instead of executing immediately
- [ ] Queue flushed via `requestAnimationFrame`
- [ ] Duplicate effects in queue are deduplicated
- [ ] Unit tests verify:
  - Multiple signal updates in batch → single effect run
  - Nested batches work correctly
  - Effects run in correct order

## Implementation

Batching scheduler implemented in `domius-core/src/runtime.rs` with:

- `EFFECT_QUEUE`, `IN_BATCH` and `FLUSH_SCHEDULED` TLS state
- `schedule_effect` enqueues effects when in a batch and deduplicates
- `schedule_flush_if_needed` uses `requestAnimationFrame` on wasm and synchronous flush otherwise
- `batch()` API provided to group updates

Unit tests demonstrate that batching deduplicates and runs effects once per batch (`cargo test -p domius-core`).

## Code Structure

```rust
thread_local! {
    static BATCH_QUEUE: RefCell<Vec<Rc<Effect>>> = RefCell::new(Vec::new());
    static IN_BATCH: RefCell<bool> = RefCell::new(false);
}

pub fn batch<F: FnOnce()>(f: F) {
    IN_BATCH.with(|b| *b.borrow_mut() = true);
    f();
    IN_BATCH.with(|b| *b.borrow_mut() = false);
    flush_queue();
}

fn flush_queue() {

}
```

## Testing Strategy

```rust
#[test]
fn test_batching() {
    let a = signal(0);
    let b = signal(0);
    let mut runs = 0;

    let (a_clone, b_clone) = (a.clone(), b.clone());
    create_effect(move || {
        a_clone.get();
        b_clone.get();
        runs += 1;
    });

    batch(|| {
        a.set(1);
        b.set(2);
    });
    // Effect runs only once, not twice
    assert_eq!(runs, 2); // initial + batch
}
```
